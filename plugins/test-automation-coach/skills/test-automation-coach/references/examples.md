## Mode A, short (Russian)

**User:** «Что такое автотест простыми словами?»

**Response:**
Тест — это проверка, что что-то соответствует ожидаемому. Мама просит сына сходить в магазин и проверить, есть ли там нужное молоко: дойти до магазина — это предусловие, посмотреть на полку — проверка. Автотест — те же шаги и та же проверка, только выполняет их программа: сама «доходит» до нужного места в продукте, сама проверяет и сообщает «всё ок» или «вот здесь не так».

Зачем: программа делает это за секунды, хоть после каждого изменения кода, и не устаёт. Чего она не умеет — заметить то, что в неё не заложили; поэтому ручное тестирование не исчезает.

Хотите — расскажу, какие бывают автотесты (пирамида тестирования) и когда автоматизировать не стоит.

## Mode B, full (Russian, abbreviated)

**User:** «Попросили автоматизировать регресс админки: 120 ручных кейсов, прогон руками 2 дня, релиз раз в 2 недели. Админка живёт давно и будет развиваться. Стоит?»

**Response (structure):**
1. **Короткий ответ:** да, но не всё и не через UI в первую очередь.
2. **Критерии:** за — частые прогоны (каждый релиз), долгий ручной прогон, продукт долгоживущий; против — UI админки часто меняется (уточнить), часть кейсов может быть дешевле руками.
3. **Окупаемость (допущения помечены):** создание: ручной кейс уже есть (Cm≈0), автотест ~3 ч; прогон руками ~16 мин на кейс (2 дня / 120), автоматически ~1 мин машинного времени; поддержка автотеста за год ~4 ч, ручного ~1 ч. → безубыточность после ~N прогонов; при 26 релизах в год окупается примерно за X месяцев. Если поддержка UI-теста окажется 10 ч в год — срок вырастает до Y. Формула не учитывает: раннее обнаружение багов (+), освобождённое время тестировщиков (+), задержки релизов из-за ложных падений (−).
4. **Варианты:** (а) оставить руками, улучшить чек-лист; (б) логику и данные — через API-тесты, в UI — 10–15 ключевых сценариев, остальное чек-листом; (в) автоматизировать все 120 через UI. **Рекомендация: (б)**, почему.
5. **Как сказать руководителю:** 2–3 фразы с цифрами.

## Mode C, opening of a full answer (English)

**User:** "I'm the first QA in a 10-person startup. No tests, devs deploy straight to prod. Where do I start?"

**Response (structure):** diagnosis questions answered or assumed → stage 1: how tasks are written (Why / What / DoD / acceptance criteria) and QA in planning — before any test code → stage 2: developers' unit tests (show by breaking code; rule for new code from date X; coverage on PRs) → stage 3: API tests on a per-PR environment with results back in the PR → stage 4: a handful of UI/E2E scenarios, also on prod as monitoring → stage 5: readable reports, status page, README and a demo for the team → what to measure. Each stage: why, options, recommendation.

## Mode D, one review finding (Russian)

**Важное — перепараметризация (`checkOrder`, строки 40–71).**
Что: один параметризованный тест с 6 параметрами, флагами `checkDiscount` и `skipDeliveryIfPickup` и необязательным колбэком. По строке `{2, true, "promo", false, null, 200}` невозможно понять, что проверяется.
Почему плохо: любое изменение надо мысленно прогнать через все наборы; новый тип заказа добавит ещё флаг и ещё `if` — тест превращается в несколько тестов, склеенных условиями.
Как исправить: отдельные тесты на доставку, самовывоз и промокод; общие шаги — в методы клиента; параметризовать только кейсы, где различаются одни данные, и собрать данные в объект `TestData` с именованными полями.
